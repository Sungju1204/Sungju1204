### 1. Tokyo Collective — 실제 운영 중인 빈티지 의류 판매 사이트
> 직접 중고로 판매하는 의류를 소개하는 쇼핑몰. 중고 거래 플랫폼 FruitsFamily의 판매자 페이지와 15분마다 자동 동기화하고, 구매는 원본 판매 링크로 연결합니다.

- **기간 / 인원 / 역할**: 2026.08 ~ 운영 중 / 개인 프로젝트 / 기획, 설계, 프론트엔드, 백엔드, 배포, 운영 전부 담당 (AI 코딩 도구 Claude Code 활용)
- **스택**: Vue 3, Vue Router, Pinia, Vite · Node.js, Express · SQLite(개발), Turso/libSQL(운영) · Vercel 서버리스, GitHub Actions, cron-job.org · Vitest
- **구조**: Vue SPA → Vercel 서버리스로 올린 Express API → Turso DB. 외부 크론이 15분마다 동기화 API를 호출해 FruitsFamily 판매자 페이지를 스크래핑하고 DB에 반영
- **한 일**
  - 상품 목록, 장바구니, 주문 기록(결제 없이 주문 정보만 저장) 구현
  - 관리자 대시보드: 로그인 후 상품 등록·수정·삭제, 주문 확인, 재고 관리
  - FruitsFamily 자동 동기화: 신규 상품 등록, 품절/재입고 반영, 삭제된 상품 제거, 이름·가격 갱신
  - API 라우트별 인증 분리(공개 / 관리자 토큰 / 동기화 전용 시크릿 헤더), 환경 변수로 개발(SQLite)과 운영(Turso) DB 전환
  - master 브랜치 푸시 시 Vercel 자동 배포, 네트워크와 DB 없이 도는 핵심 로직 테스트(Vitest)
- **설계 포인트: 멈추지 않는 동기화**
  - 동기화가 한 번 빠지면 이미 팔린 옷이 사이트에 계속 남습니다. 그래서 cron-job.org를 주 경로로, GitHub Actions를 백업으로 두어 스케줄러를 이중화했습니다.
  - 스크래핑이 실패하면 변경 사항을 반영하지 않도록 해서, 일부만 긁힌 데이터로 멀쩡한 상품이 삭제되는 일을 막았습니다.

### 2. InfoMate — AI 가짜뉴스 판별 서비스
> 뉴스 URL을 입력하면 AI가 출처, 편향성, 광고성을 분석해 0~100점 신뢰도를 알려주는 웹 서비스

- **기간 / 인원 / 역할**: 2025.09 ~ 2025.12 (최종 발표 12/8) / 4명 (프론트엔드, 백엔드, 데이터 수집, 협업) / **팀장 · 프론트엔드 담당**, 백엔드 안정화 작업 공동 진행
- **스택**: Vue 3 (Composition API), Vite, Axios, Notion(일정·작업 관리) · (팀) Django, BeautifulSoup, PyTorch (KLUE/roberta-small), Nginx, Docker Compose
- **구조**: Vue에서 URL 전송 → Django API가 기사 크롤링(BeautifulSoup) → KLUE/roberta-small 모델로 신뢰도 추론 → JSON 결과를 Vue에서 표시
- **한 일**
  - **팀장**: 4명의 역할(프론트엔드, 백엔드, 데이터 수집, 협업)을 분배하고, 프론트/백엔드 주차별 마일스톤과 Notion 작업 보드를 만들어 일정 관리. 정기 회의를 진행하고 중간·최종 발표 담당
  - 팀원이 막힌 부분을 함께 해결: 백엔드 담당 팀원과 안정화 작업(아래)을 같이 진행하는 등 파트를 넘나들며 지원
  - API 통신 계층 설계: `services/api.js`로 통신 코드를 분리하고 API 주소를 환경 변수로 관리해 개발/운영 환경 전환이 쉽도록 구성
  - 분석 요청 흐름 구현: URL 유효성 검사, 분석 API 호출, 백엔드와 연동 테스트(Postman, CORS 확인)
  - 분석 결과 화면(AnalysisResult 컴포넌트) 구현
  - 대기 경험 개선: 로딩 스피너와 예상 소요 시간 표시, 에러 메시지 개선과 재시도 버튼
  - 백엔드 담당 팀원과 함께 URL 입력 검증, 크롤링·모델 추론 타임아웃, Rate Limiting, 요청/에러 로깅, 같은 URL 재요청을 막는 캐싱, 모델 추론 속도 개선, 응답 시간 모니터링 진행
- **트러블슈팅: 느린 분석 응답과 대기 경험 개선**
  - **문제**: 분석 한 번에 기사 크롤링과 AI 모델 추론을 차례로 거쳐서 응답이 늦었습니다. 기다리는 동안 사용자는 진행 상황을 알 수 없었고, 크롤링이나 추론이 지연되면 응답이 아예 오지 않는 경우가 있었습니다. 같은 기사를 다시 넣어도 매번 처음부터 분석했습니다.
  - **해결**
    - 프론트엔드: 로딩 스피너와 예상 소요 시간을 보여주고, 실패하면 원인별 에러 메시지와 재시도 버튼을 띄우도록 했습니다.
    - 백엔드(백엔드 담당 팀원과 함께): 크롤링과 모델 추론에 타임아웃을 걸고, 같은 URL은 이전 결과를 캐싱해 바로 돌려주도록 했습니다. 응답 시간을 모니터링하면서 모델 추론 속도도 개선했습니다.
  - **배운 점**: 응답 시간은 백엔드 성능만의 문제가 아니었습니다. 기다리는 동안 무엇을 보여주는지, 실패했을 때 어떻게 안내하는지에 따라 사용자 경험이 크게 달라진다는 것을 배웠습니다. 그래서 프론트와 백엔드 양쪽에서 함께 대응했습니다.
  <!-- 개선 전후 응답 시간 같은 실제 수치가 있으면 결과 줄에 추가하세요. 예) 같은 URL 재요청 시 응답 시간 N초 → M초 -->
- **배운 점**: 파트별로 나눠 개발하더라도 문제는 경계에서 생긴다는 것. API 요청·응답 형식과 에러 코드를 초기에 백엔드와 합의하고 문서화한 덕분에 연동 과정이 수월했습니다.
